## 三个必须记住的坑（都踩了）
1. **ABI 绝对不能锁成 armeabi-v7a(ARM32)**：
   x86 模拟器(BlueStacks) 的 ARM 转译层加载 .NET 运行时会
   `dlopen failed: failed to link libmono-android.release.so` → 启动即崩。
   用 .NET 默认 ABI（**arm64-v8a + x86_64**）→ BlueStacks 走 x86_64 原生，正常。
   （对照实验：`dotnet new android` 默认模板在 BlueStacks 上跑得起来，就是 arm64-v8a+x86_64。）
2. **不要设 `AndroidEnableAssemblyCompression=false`**（那是合并方案遗留的）：
   它让生成的 `libxamarin-app.so` 缺少 `compressed_assembly_count` 符号，
   `libmonodroid.so` 链接失败：`cannot locate symbol "compressed_assembly_count"`。
   合并方案废弃后，所有 assembly 相关属性都回归默认值。
3. **改完 ABI/打包属性后必须真·clean build**：否则 typemap/assembly store 是旧的，
   启动会 `No implementation found for ... n_onCreate()`。
   （`rm -rf obj bin` 被安全守卫拦了，改用 `mv obj /e/bo-stale/obj` 挪走。）

## 构建（★ 必须走 ASCII 路径，否则 aapt2 APT2265）
- **项目路径含中文 → aapt2 无法读 `-A <assets>` 目录**（报 `系统找不到指定的文件` → APT2265）。
- 解决：建了**目录联接** `E:\boj → E:\逆向工程\苍蓝誓约项目`（`New-Item -ItemType Junction`），
  用 `dotnet build "E:/boj/src/BlueOath.Android/BlueOath.Android.csproj" -c Release -p:UseSharedCompilation=false`。
- `-p:UseSharedCompilation=false` 用于绕开 VBCSCompiler 锁 DLL(CS2012)；
  或先 `dotnet build-server shutdown`。
- 产物：`src/BlueOath.Android/bin/Release/net10.0-android/com.blueoath.server-Signed.apk`（~54MB）。

## 环境坑
- **`keep_reverse.sh` 后台保活会一直重加 adb reverse**（19090/19191/19192/19193），
  导致 App 绑定端口时 `SocketException: Address already in use`。必须先杀掉它（我用 PowerShell
  `Stop-Process -Id <pid> -Force`，用 `Get-CimInstance Win32_Process` 找 `bash.exe keep_reverse.sh`）。
- 杀掉它之后 adb daemon 会重启 → 需要重新 `connect 127.0.0.1:5555`。
- adb daemon 反复自己重启，**每个命令都要先 connect**；GD-Adb 建议统一用 `MSYS_NO_PATHCONV=1`，
  否则 `/sdcard/...` 会被 MSYS 转成 `E:/S/...`。
- BlueStacks 自带 adb：`C:/Program Files/BlueStacks_nxt_cn/HD-Adb.exe`，`connect 127.0.0.1:5555`。

## 端到端验证结果（重要）
模拟器实况：服务端 App 正常 Ready，游戏成功连上它并走完引导：
```
capture[1] POST /phone/switch/getstate
capture[2] POST /phone/applereview/
capture[3] POST /phone/getPlData/getPlData/
capture[4] POST /phone/getversion/          ← 返回 src/tar_version=1.4.140（正确）
capture[5] POST /index.php?
```
**但卡在热更 assetmap**：客户端下载 `assetmap_1.4.140`，CDN 基址
`http://127.0.0.1:19090/windows_android/`，NetworkFailTimes:5 →
弹窗「アップデートリストの読み込みに失敗しました」。

原因：`EmbeddedServer` 之前给 `ServerOptions.BundleRoot` 传了 **null**
（PC 侧 `run_server.sh` 是 `--bundle-root="$ROOT/android/_work2/merged"`）。
实测 `https://127.0.0.1:19090/windows_android/assetmap` → **501**（未实现），
而 `/phone/getversion/` → 200，说明 TLS/路由本身没问题。

已修：`EmbeddedServer` 增加 bundle 根解析
- 目录：`Context.GetExternalFilesDir(null)/bundle`（= `/sdcard/Android/data/com.blueoath.server/files/bundle`，免存储权限），
  内部目录 `filesDir/bundle` 作回退；**必须含 `assetmap` 才认**。
- UI 提示里显示该路径；日志打印 `bundle root: <path>`。
- ★ 该 bundle 来自 `android/_work2/merged`（**3.5GB**，含 assetmap/bundles/atlases/characters/...），
  太大无法塞进 APK，需**拷到设备**该目录（实测 `adb push 单个条目` 可行；
  注意 `/sdcard/Android/data/<pkg>/files` 目录要先 `mkdir -p`，否则 adb push 报
  `secure_mkdirs failed: Operation not permitted`）。

另外：客户端服务器交互走 **HTTPS**（即便 getversion 里 static_url 写的是 http://），
我们的 19090 TLS 没问题，不用再单开 TLS 代理。

## ★ 热更下载打通全过程（最后一公里，逐层踩坑）

客户端最终**成功拿到 assetmap**，标题页不再弹「アップデートリストの読み込みに失敗」，
进入 1.4.140 的「更新」热更页。要让下载真正跑起来，依次解决了 4 层：

1. **协议层**：热更下载走客户端**原生 libcurl/7.52.1 + OpenSSL**（`BTHttpClient.cpp`），
   自带 CA 校验，**不走客户端侧 SSL 绕过** → 自签 TLS 会被拒。
   故 `EmbeddedServer` 另开一个**明文 HTTP 端口 19193**（`BundleHttpServer`）专供下载，
   并通过新参数 `ServerOptions.BundleStaticBaseUrl`（`--bundle-static-url=`）把
   `http://127.0.0.1:19193/` 写进 getversion 的 `static_url`。
   （`BootstrapHttpResponder` 里 static_url 以前硬编码 `http://127.0.0.1:<主端口>/`。）

2. **★★ 设备全局 HTTP 代理**：BlueStacks 上设了 `global http_proxy = 192.168.2.230:1081`，
   **libcurl 会对 127.0.0.1 也走代理** → 连接失败，服务端日志里**一条请求都看不到**。
   清掉即可：`adb shell settings put global http_proxy :0`
   （设 `global_http_proxy_exclusion_list=127.0.0.1` 实测**不够**，必须清掉 host）。

3. **请求名带后缀**：客户端请求的是 `GET /windows_android/assetmap_1.4.140`，
   而真实文件叫 `assetmap`。原来的「仅当后缀全为数字才剥」规则对 `1.4.140`（带点）失效
   → 404。已改为**逐个剥 `_xxx` 后缀取第一个存在的文件**（`BundleHttpServer.Resolve`）。

4. **bundle 上机**：`android/_work2/merged`（3.5GB / 6738 文件）要拷到
   `/sdcard/Android/data/com.blueoath.server/files/bundle`（App 专属外部目录，免权限）。
   ⚠️ 本机 **adb push 无法创建嵌套目录**（`secure_mkdirs failed: Operation not permitted`），
   但 `adb shell mkdir -p` 可以 → 脚本 `android/_work/push_bundle.sh`：
   先生成目录清单 push 上去、用设备侧 shell 循环 mkdir，再按顶层条目 push。
   注意清单文件也要用 ASCII 路径（`/tmp/...` 在 MSYS_NO_PATHCONV 下会变成 `E:\tmp` 而失败）。

调试要点：`BundleHttpServer` 会打印 `bundle-req <请求行> -> <状态> (<字节数>)`，
用来判断「客户端到底有没有连上/请求什么路径」。

## ★★ 后来发现的真正根因：宣告版本号必须 = 客户端内嵌 assetmap 版本（1.4.90）
用户提示后定位到：**客户端标题页「パージョン内容」= 1.4.90**（= APK 内嵌 assetmap 版本），
而 `EmbeddedServer` 一直宣告 `ClientVersion = "1.4.140"`（照搬 PC 的 run_server.sh）。
版本不一致 → 客户端走 **PATCH_TO_LATEST**（要真下载），于是永远停在热更/下载界面。

改成 `ClientVersion = "1.4.90"` 后：
- getversion 返回 `src_version=tar_version=1.4.90`、`updateType=0`
- 客户端 **不再进热更页**，直接加载出**真正的标题画面**（左上角两个版本号都 1.4.90）
- **热更错误 0 条**（此前一直报「アップデートリストの読み込みに失敗」）

★ 这条项目笔记里早有记载（`tar_version 必须 == 客户端 assetmap 内嵌版本`），
  之前照搬 PC 的 1.4.140 才导致整条热更链路白折腾。

## 预置资源（push）实测结论
- **版本对齐前**：把资源 push 到 `<game>/files/bundles/` 后，客户端下次启动会**清空并重下**。
- **版本对齐后**：push 进去的资源**被接受了**（不再清空、不再发下载请求，`bundle-req` 计数 0），
  但游戏随后在 `AssetLoaderManager.ClearUnres` 抛 NullReference 死循环（黑屏）——
  说明**光预置文件还不够**，客户端自己那套「下载/校验完成」的初始化流程没跑，资源管理器没被建起来。

- 客户端资源落地目录：`/sdcard/Android/data/com.zephyrus.clsy.gp/files/bundles/`
  （结构与 `_work2/merged` 一致；它把下载到的 assetmap 存成 `assetmap_target`）。
- push 脚本可直接指定目标：`SKIP_ENTRIES="assetmap" push_bundle.sh <game>/files/bundles`

## ★★★ 最终打通：缺的那 0.28MB = merged 里的 config_language.db 是错的
用户提示「热更页点修復后显示还差 0.28MB」。查服务端 bundle-req 日志，找到唯一反复 404 的请求：
```
GET /windows_android/compressed/config/config_language.db_C1FB863A82E1A797FDFAD268A2B3ECB4 -> 404
```
（后缀 = assetmap 的校验字段；客户端只反复要这一个文件 → 只有它不对。）

### 根因
`android/_work2/merged/config/config_language.db` 是**旧 overlay / PC 版的错误副本**：
体积相同（823296）但 md5 = `8ba39fb80a00ee81991dbc41dd6a3ece`，
而 assetmap（`new_assetmap.txt`）要求 `C1FB863A82E1A797FDFAD268A2B3ECB4`。
—— `build_merged.py` 是按 **size** 选源的，同尺寸不同内容就会选错。
**正确文件在 `android/_work2/new_bundles/config/config_language.db`（md5 恰好 = C1FB86…）**。

### 修法
1. `cp new_bundles/config/config_language.db merged/config/config_language.db`（旧的另存 `.wrong-overlay`）
2. 推到两处：服务端 `/sdcard/Android/data/com.blueoath.server/files/bundle/config/` +
   游戏 `/sdcard/Android/data/com.zephyrus.clsy.gp/files/bundles/config/`
3. 重启游戏 → 弹窗变成「ダウンロードには **0.00MB** が必要」，点確認 → 一路进到标题页

### 新增工具
`android/_work2/verify_merged.py` —— 用 `new_assetmap.txt` 全量校验 merged（md5+size）。
本次结果（1397 条普通文件）：OK 952 / 大小不符 0 / **md5 不符只有 config_language.db 这 1 个**；
另有 444 条 `config/config_*.db` 报「缺失」，但它们来自 assetmap 的另一段，
客户端并不索取（由 APK 基线满足），**不必补**。

### 最终状态（实拍）
- `bundle-req` 只剩 1 次 assetmap(200)，**404 = 0**，热更错误 = 0
- 完整登录链跑通：
  `getagreeversion → sdklogin(devicelogin) → getuserextra → /phone/login → getPlatformUserInfo
   → serverlist → loginrole`
- 标题页显示 **サーバー選択: BlueoathRebirth** + 「Press to start / 出撃」，即可进游戏

### 结论（回答用户「为什么之前能过」）
之前能过，是因为**设备 sdcard 上早就躺着 3.0G 的 1.4.140 资源**（游戏自己下好的），
服务端配 `--client-version=1.4.140` 与之匹配 → 不热更 → 直接登录。
我们这次 `pm clear` 把这批资源（含正确的 assetmap 与 config_language.db）清掉了，
才重新暴露「版本/资源」问题；而 merged 里那个错的 config_language.db 一直存在，
只是以前设备上有正确副本，所以没暴露。
→ **正确姿势**：把 1.4.140 资源（含 `bundles/assetmap`）放回游戏目录 + 服务端 1.4.140。
