0x00FC4838: bl   #0x25b726c      ; 查「是否在外部文件集」→ 返回 bool

### ★ assetmap 的**三段结构**（此前只解析了第一段）
```
第1行: 版本号 (如 1.4.140)
段A: <rel>,<crc数字>,<md5>,<size>          ← bundle，5768 条
段B: <资源名列表>,...                       ← 资源名→bundle 映射
段C: <rel>,<32位真实MD5>,<size>,<compressedSize> ← md5File，1397 条
```
- **段C 的 md5 是标准 MD5**（可用 hashlib 精确校验）
- **段A 的 crc 字段不是标准 CRC32，其 md5 字段也不是真 MD5**
  （`bundles` 的值为 `00000000000000000000000007d520d2`，仅低 4 字节非零）
  → 段A **只能用 size 判据**（实测有效，游戏 0 次 CRC 错误）
- 客户端 `GetExternalMd5s`/`GetExternalBundles` 决定哪些文件需要外部化：
  **与 APK 内置一致 → 读 APK，无需下载；否则必须在 sdcard**

# ★ 证书校验问题：根因定位与修复（方案 H）

## 一、根因链（推翻此前假设）

此前认为「Java 侧 `newsdk.base.BaseSdk.httpGet` 校验证书」。**实测证明不是**：

1. 报错行：`I/System.out: java.security.cert.CertPathValidatorException: Trust anchor for certification path not found.`
   每 **10 秒** 一次（Timer 定时任务）
2. 完整堆栈：`HainaReport.init(HainaReport.java:103)` ← `BaseSdk$2.run(BaseSdk.java:287)` ← `TimerThread.mainLoop`
   —— 是 **埋点上报**（海纳 `HainaReport`），不是登录
3. **两个 SDK 的 HTTP 客户端都是 TrustAll**：
   - `com.bt.http.HttpClient`：`trustAllCert` 的 `checkServerTrusted` 只判参数非空，**不校验证书链**，
     并用 `sslSocketFactory(sslSocketFactory, trustAllCert)` 塞进 OkHttpClient
   - `com.gamesdk.http.HttpClient`：同上（`SSLSocketFactoryCompat(trustAllCert)`）
   → **游戏业务请求（含登录 httpGet）不受证书影响**
4. 真正校验证书的是 **WebView / Chromium 自己的 net stack**：
   `HainaReport` 用 WebView 加载 `https://127.0.0.1:19090/c.gif` 上报埋点
   （日志可见 `cr_WVCFactoryProvider` / `chromium` 初始化，随后立刻抛异常）

结论：证书问题只影响 **WebView 类流量**（埋点 + 后续 SDK 登录/公告 WebView），不阻塞当前登录。

## 二、修复方案：networkSecurityConfig + 内置根证书

APK 事实：`targetSdkVersion=30`（默认只信系统 CA）、`android:usesCleartextTraffic="true"`（已允许明文）。

注入内容：
- `res/xml/network_security_config.xml`
  ```xml
  <network-security-config>
    <base-config cleartextTrafficPermitted="true">
      <trust-anchors>
        <certificates src="system"/>
        <certificates src="user"/>
        <certificates src="@raw/blueoath_root"/>
      </trust-anchors>
    </base-config>
  </network-security-config>
  ```
- `res/raw/blueoath_root.cer` = `runtime/tls/blueoath-local-root.cer`（**DER**，797 B）
- `AndroidManifest.xml` 的 `<application>` 加 `android:networkSecurityConfig="@xml/network_security_config"`

作用域：Android 7+ 的 **WebView 也遵守 networkSecurityConfig** → 一并解决 Chromium 的信任问题。

## 三、重打包方法（可复用）

`apktool` 无法整体重打包 1.1GB APK（assets 1GB），采用 **「只取 manifest/arsc/res，其余从原 APK 合并」**：

1. `apktool d -f -s --no-assets -o planG_dec planG.apk`
   （`-s` 不反编译 dex；`--no-assets` 跳过 1GB assets；解包仅 ~120MB）
2. 改 `AndroidManifest.xml`（文本）+ 放 `res/xml/network_security_config.xml` + `res/raw/blueoath_root.cer`
3. `apktool b planG_dec -o planH_small.apk` → 58MB（含新 arsc + res + manifest）
4. `build_apk_h2.py`：以 planG 为基础，
   - 跳过 planG 的 **全部 `res/`**
   - 替换 `AndroidManifest.xml` + `resources.arsc`
   - 写入 apktool 的 **全部 `res/`（929 个）**
   - assets/lib/dex 等全部沿用 planG
5. `fix_zip64.py` → `zipalign -p -f 4` → `apksigner sign --v1 --v2 --v3`

### ★ 关键坑：aapt2 会规范化资源目录名
planG 里是 `res/drawable-hdpi-v4/gamesdk_loading.png`，
apktool 产物里变成 `res/drawable-hdpi/gamesdk_loading.png`（**去掉 `-v4`**），
共 **536 个** res 路径被改写。
→ 若只替换 arsc 而沿用原 res/，会 `Resources$NotFoundException: drawable/gamesdk_loading`
   （资源 ID `0x7f0200a9`）→ **游戏启动即崩**。
→ **必须整体采用 apktool 输出的 `res/`**，不能只换 arsc。

### 资源 ID 保留已验证
`planG_dec/res/values/public.xml` 有 2238 条固定 ID；新 arsc 的 `spec resource` 完全一致
（0x7f010000 起逐个对齐）→ dex/native 中硬编码的 R 引用不会错位。

# ★ 为什么安卓端收不到服务器列表（诊断 + 修复）

## 结论
服务端**有** `/phone/serverlist/`（返回 BlueoathRebirth）；安卓端**从未请求它**。
根因：**PC 版与安卓版的登录走的不是同一套 SDK 通道**，而服务端只实现了 PC 版那一套。

## 两条通道对比
| | PC 版 | 安卓版 |
|---|---|---|
| SDK | native `new_sdk.dll` | Java `com.gamesdk`（+ native libnew_sdk.so）|
| 登录接口 | `POST /login?` | `GET /sdk/sdklogin?action=devicelogin` |
| 服务端实现 | ✅ 已有 | ❌ 原先没有 → 501 → 登录失败 → 流程中断 |

证据：
- `new_sdk.dll` 与 `libnew_sdk.so` **都**含 `/login?` 字符串；但安卓版实际没走 native 登录

  `httpGet(BASE_LOGIN_URL + sdkLogin, ...)`

# ★★★ 重大突破：/phone/login 崩溃元凶 = `newuser` 字段

## 一、定位方法（比 tombstone 更有效）

- ★ 真机最大门槛：**是否支持 32 位 armeabi-v7a**（游戏只有 v7a）。
  脚本会读 `ro.product.cpu.abilist`，不含 armeabi-v7a 就退出并提示换设备
  （部分新旗舰已移除 32 位支持 → 装不上，这条路就断了）。
- 首次安装后游戏会从本地服务端拉热更资源（走 USB loopback，可能较慢）；
  备选是 adb push 到 sdcard（Android 11+ 作用域存储能否写入 App 目录待实测）。
- 真机每次重新插拔 USB，reverse 会丢失 → 重跑脚本第 [5] 步。

# ★ 真机验证实测结论（2026-10-09 晚）：Galaxy S25 Ultra **不可用于本游戏**

## 实测数据（adb 实读，确凿）
真机识别：`R5CY929803T  product:pa3qzcx  model:SM-S9380  device:pa3q  board:sun`
- `ro.product.cpu.abi      = arm64-v8a`
- `ro.product.cpu.abilist  = arm64-v8a`      ← 只有 64 位
- `ro.product.cpu.abilist32 = (空)`          ← ★ 无 32 位 ABI
- `ro.product.cpu.abilist64 = arm64-v8a`
- `ro.hardware = qcom`（Snapdragon 8 Elite / SM8750）
- `ro.build.version.release = 16`, `sdk = 36`

## 结论
Snapdragon 8 Elite **CPU 层面移除了 AArch32**，Android PackageManager 按 abilist 判定
→ 游戏 APK 只有 `armeabi-v7a`（**原始官方日服 APK 也只有 armeabi-v7a**，非我们打包所致）
→ `INSTALL_FAILED_NO_MATCHING_ABIS`，**硬件限制，不可通过补丁/配置绕过**。

已校验项目内全部 34 个 APK，native ABI 一律 `['armeabi-v7a']`，不存在 arm64 版本。

## 影响范围（重要）
不只是真机验证：**自包含方案的最终设备也必须支持 armeabi-v7a**。
S25 Ultra 这类纯 64 位机型永远跑不了该游戏 —— 选设备时先查 `ro.product.cpu.abilist32` 非空。

## adb 环境坑（真机验证时必踩）
- BlueStacks 的 `HD-Adb.exe`(v36) 与 platform-tools(v41) **互抢 5037**，互相 kill；
  表现：`adb server version (36) doesn't match this client (41); killing...`
- 反复 `kill-server` 会让 USB 真机掉成 **offline**（需重新插拔）。
- 5038 备用端口看不到 USB 设备（USB 被先启动的 server 独占）。
- ★ 根治办法：真机验证时**彻底退出 BlueStacks**（含后台服务），
  或改用**无线调试**（`adb pair` + `adb connect ip:port`，走 TCP，完全避开 USB 与 5037 争抢，
  且 adb reverse 对 TCP 设备同样有效）。

## 候选设备快检命令
```bash
adb shell getprop ro.product.cpu.abilist32   # 非空 = 支持 32 位 = 可用
adb shell getprop ro.product.cpu.abilist
```
支持 32 位的机型参考：Snapdragon 8 Gen 3 及更早（Samsung S21/S22/S23 系列等），
2023 年前机型基本都可用。

## ★ start_all.sh 教训（重要）
- `nohup cmd &` 在**用户自己的 Git Bash 窗口**完全存活；
  但在 **AI Agent 的 Bash 工具**里，命令结束时后台子进程会被回收
  → 表现：脚本内显示"✅ 已监听"，随后 netstat 全空、游戏报「電波が安定していません」
- Agent 环境下服务端/TLS 代理/保活必须用**工具级后台任务**（run_in_background）逐个跑；
  keep_reverse.sh 也一样（且它内层 heredoc/stdin 消费注意）。
- `cmd //c start ... cmd //c "..."` 嵌套引号在 MSYS 下不可靠（会落入交互模式挂起会话），放弃该方案。
- 脚本流程 bug：`while read <<EOF` 循环内 adb 会吞 stdin → 只跑第一个迭代就退出。改用数组 for。

## 现行可靠启动方式
- 用户终端：`bash android/_work/start_all.sh`（nohup 方案）
- Agent 会话：服务端(g4mEgq)、TLS代理(A3F1UF)、keep_reverse(0p8jrr) 三个后台任务
