### Android 与 PC 的关键差异（决定复原路线）
1. **重定向手段完全不同**：Android 无 Winsock IAT。PC 用的 `getaddrinfo`/`connect`/`curl` IAT + `UnityPlayer.dll` RVA patch 全部不适用。
2. **SDK 有 HTTPDNS**：`libnew_sdk.so` 含 `bt::HttpDNS` / `bt::DNSAli` / `bt::DNSTencent` / `fetchIp` / `setIpsToLocal` / `getHost` / `getLogHost`。
   → **改 hosts / 常规 DNS 会被 HTTPDNS 绕过**。但导出符号里有 `setIpsToLocal`，是**官方自带的本地 IP 覆盖入口**，可作为重定向注入点。
3. **SDK 是 native + Java 的**：`new_sdk` 在 Android 是 `libnew_sdk.so`(C++) + `classes*.dex`(Java)，PC 上的 `new_sdk.dll` hook（SHA 门控 + RVA 0x3A850）不可复用，需重新定位。
4. **TLS 证书校验点不同**：PC 是 `UnityPlayer.dll!0x8E1573` mask NOT_TRUSTED。Android 在 `libunity.so` / `libil2cpp.so` 内的 mbedTLS/BoringSSL，需重新定位；也可用 Frida 在运行时定位。
5. **登录入口不同**：PC 走 `BabelTimeSDKManager.Login`(RVA 0x2D1870) + `new_sdk.login`。Android 是 Java `com.platform.main.sdk.*` + native，需重新挂钩。
6. **传输协议本身应当一致**：11 字节应用层头 + protobuf 信封 + KCP over UDP 是**游戏逻辑层**，与平台无关 → **PC 服务端可复用，理论上不用改协议**（仅需验证 JP 1.4.90 与 1.4.0 的协议增量）。
7. `libxlua.so` 存在且 Lua 同为 5.3.5 → **Mod（xLua loader）思路在 Android 上同样可行**。

### 候选路线（方案文档待写）
- 路线 A：**Frida 动态注入**（无需改包，调试期最快；用 Frida 挂 `getaddrinfo`/`connect`/HTTPDNS/`SSL_verify`）。缺点依赖 root + frida-server。

## ★ 热更 bundle 下载链路打通（2026-10-05 11:40）

### 结论：客户端已能真实从本地服务器下载热更包

服务端新增 `/windows_android/<rel>` 路由后，模拟器客户端点击「ダウンロード」会真的


### 关键机制：URL 的 `_<crc>` 后缀是客户端拼的，不是文件名的一部分

- `BundleDownloadInfo.GetPostFix()`（PC `0x207C60`）= `"_" + crc.ToString()`；
  `DownloadInfo` 字段布局 `name(0x8)/needDownloadSize(0x10)/isCompressed(0x18)/state(0x1C)`，
  `BundleDownloadInfo.crc` 在 `0x20`；反汇编即 `add [ebp+8],0x20` 后 tail-call uint→string。
- `IsDownloadCorrect(path)`（PC `0x207C80`）只校验路径**后缀**匹配，不做内容 CRC。
- 所以服务端必须**先剥离尾部 `_<纯数字>` 再查表**。真实文件名 = assetmap 里的 key。

### assetmap 的权威格式（从 APK 内 `assets/assetpack/bundles/assetmap` 解出）

UnityFS(2018.2.4f1, flags 0x43) —— blocksInfo 在 **header(49) 之后**（不是文件末尾，

## ★★ 关键突破（12:20）：缓存 zip 的 bundle 与 assetmap 版本不一致

### adb 推送踩坑（Git Bash 路径转换）

1. **`adb push src/ dst/` 会被 MSYS 把 `/sdcard/...` 转成 `C:/Users/.../PortableGit/sdcard/...`**
   → 必须 `export MSYS_NO_PATHCONV=1; export MSYS2_ARG_CONV_EXCL='*'`。
2. **push 到 `/sdcard/Android/data/<pkg>/` 会 `remote fchown failed: Operation not permitted`**
   （FUSE 不允许改属主）→ 先 push 到 `/data/local/tmp/`，再 `adb shell cp` 到目标。
3. 大批量用 **tar**：本地 `tar -cf x.tar dir` → push → 设备 `tar -xf`（chown 报错可忽略）
   → `cp -r /data/local/tmp/bex/bundles/. $DST/`。比逐文件 push 快得多。

| 来源 | 与 assetmap 尺寸一致性 |

## 方案B 构建 & 部署（收尾阶段）

### 构建链路全线打通（关键坑位记录）

**坑1：Python zipfile 生成"半 ZIP64"结构 → zipalign/apksigner 全部失败**
- 现象：`zipalign` 报 `Unable to open ... as zip archive: No error`；
  `apksigner` 报 `offset (2161243729) + size (2133723566) > source size`（两者之和恰为 0xFFFFFFFF）
- 真因：Python zipfile 在写大归档时，即使各 32 位字段完全够用（cdOffset<4GB、条目<65535），
  仍额外写出 ZIP64 EOCD + Locator，且部分条目 header_offset 写 0xFFFFFFFF + ZIP64 extra。
  工具对这类"冗余 ZIP64"解析分歧。
- 解决：`fix_zip64.py` —— 重建中央目录，把不需要 ZIP64 的字段降级为 32 位、丢弃空 extra，
  EOCD 重写为标准格式（本例 cdoff=2447468493 < 4GB，可完全降级）。
  ★ 步进必须用**原始** efl（orig_efl），否则会漏条目（曾漏 37 个）。

**坑2：原 APK 内含 Google Play 残留签名 `META-INF/BNDLTOOL.SF|RSA|MANIFEST.MF`**
- BNDLTOOL.SF 声明 v2/v3 但 APK 内实际没有 → apksigner 误判报错
- 解决：build_apk_b.py 过滤全部 `META-INF/`

**坑3：Windows zipalign/apksigner 无法处理中文路径**（"Illegal byte sequence"）
- 解决：需复制到 ASCII 路径，或用相对路径（cd 到 _work 后操作）

**最终构建流程（可用）**
```
python build_apk_b.py            # 重建(剔除META-INF) → BlueOathJP-planB-unsigned.apk 2.28GB
python fix_zip64.py <in> <out>   # 降级ZIP64 → BlueOathJP-planB-fixed.apk
zipalign -p -f 4 fixed aligned   # → BlueOathJP-planB-aligned.apk  (Verification succesful)
apksigner sign --v1 --v2 --v3    # → BlueOathJP-planB.apk
apksigner verify                 # v1✓ v2✓ v3✓  Verifies
```
产物：`BlueOathJP-planB.apk` 2.45GB md5 `0a249622ef9f31c1d53942272daff264`

## 方案 D2'：HTTPS + TLS 代理 + patch SDK 证书校验（★ A3 阻塞点已攻克）

### 拓扑
```
客户端 https://127.0.0.1:19090
  → adb reverse tcp:19090
  → tools/tls-loopback-proxy.py (Python/OpenSSL, TLS 终止)
  → 127.0.0.1:19193 (BlueOath.Server 明文 HTTP, FrontDoorTcpListener 协议嗅探)
```

### 关键发现
1. **`--tls-auto` 在 Windows 上不可用**：.NET SslStream 用 `CopyWithPrivateKey` 生成的
   **临时私钥**，SChannel 报 `Authentication failed because the platform does not support
   ephemeral keys` / `0x8009030E 安全包中没有可用的凭证`。→ **必须用 Python/OpenSSL 代理**。
2. **客户端证书校验点在 `libnew_sdk.so`（不是 libil2cpp.so）**：
   - `libnew_sdk.so` = SDK native（`BTHttpClient.cpp` / `Platform.cpp`），静态链接 **OpenSSL**
   - `libunity.so` = UnityTLS，用 **mbedTLS**（游戏正文走 KCP/TCP 长连接，本轮不需要动）
   - `SSL_CTX_set_verify` 只有 **1 个调用点**：fileoff `0xF9384`（`bl 0x1519e8`）
   - 其前一条 `0xF9378` = `ldr r1,[sp,#0x28]`（mode 参数）→ **patch 为 `mov r1,#0`**（`0010a0e3`）
   - 编码：原始 `28109de5` → patch `0010a0e3`；后一条 bl `976101eb` 不变
3. **域名改 `https://127.0.0.1:19090`**（`game_config.json` 的 host/host_debug/track_host/crashHost
   + `urls.json` 全部 4 个 key）。不是 http 降级——保留 https 让客户端行为不变。

### 实测结果（boot_planD.log / boot_planE.log）
- **A3 完全打通**：服务端收到全部 `/phone/*` 请求，`host=127.0.0.1:19090`，
  `UnknownHostException` = 0，`网络不可用` 循环消失（仅剩 2 次 JSON 打印）。
- 新增路由（文档未记录）：`GET /sdk/getversion/getversion?os=&appid=&version=`、`GET /sdk/gettime`
  （服务端 `BootstrapHttpResponder` 已有 `/sdk/gettime`，`/sdk/getversion` 可能未实现）
- 客户端推进到 `GameApp:Awake` → `StageLaunch:StartGame` → Lua `UIPageManager:Open`（**A4 阶段**）

### ★ 致命坑：sdcard 上的 `assetmap` 必须是 1.4.90 版
overlay 是从热更缓存 zip 解出的，其 **`assetmap` 是 1.3.48 版（638346 B）**，
但**资源文件本身是 1.4.90 版**（如 `overlay/atlases/login` = 499139 = 1.4.90 期望值）。
客户端 patch 1 后走 external 路径 → 读 sdcard assetmap（1.3.48）→ 用旧 CRC 校验新资源
→ **全量 CRC Mismatch → 删除文件 → 主 bundle `bundles` 被删 → CreateMainAssetBundle 空引用**。
**修复**：push `apk_bundles/assetmap`（681825 B，1.4.90）覆盖 sdcard 上的 638346 版。
→ CRC 失败从 **356 降到 24**，`加载Bundle失败` 从多条降到 1 条。
